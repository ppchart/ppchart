# PPChart 创建预览与发布后管理设计

## 目标

补齐用户投稿的两个核心闭环：

- 用户创建或编辑图表时，可以在提交前运行隔离预览。
- 管理员可以查看已发布的用户投稿，填写原因后将其下架。

## 范围

- 仅管理通过用户投稿审核流程发布的图表，不接管历史公共图库数据。
- 复用现有 `ChartPreview`，不新建第二套图表运行器。
- 复用现有 OAuth 管理员权限，不新增权限模型。
- 不增加图片上传、批量下架或定时发布。

## 用户隔离预览

`UserChartPanel` 的编辑区改为表单与预览双栏布局：

- 左侧保留标题、版本、描述、代码和提交状态。
- 右侧使用现有 `ChartPreview` 展示当前代码。
- `ChartPreview` 继续通过带 `sandbox="allow-scripts"` 的 iframe 运行代码，用户代码不进入主页面执行上下文。
- 预览为空时展示引导文案；填写代码后可使用组件现有的“运行代码”能力重新执行。
- 移动端改为上下布局。

预览只影响前端编辑体验，不改变保存与提交 API。

## 管理端发布后管理

管理端增加两个标签页：

- `待审核`：保持现有通过与拒绝能力。
- `已发布`：查询 `user_chart.status = published` 的用户投稿，展示发布信息和运行预览。

前端 `fetchAdminCharts()` 接收 `pending` 或 `published` 状态参数。切换标签页后重新请求对应列表。

## 下架状态与 API

新增用户图表状态：

- `unpublished`：曾经发布，现已被管理员下架。

新增接口：

```text
POST /api/admin/charts/:id/unpublish
```

请求体：

```json
{
  "note": "下架原因"
}
```

规则：

- 仅管理员可调用。
- 仅 `published` 状态允许下架。
- 下架原因必填。
- 重复下架或并发操作返回 `409`。

## 下架事务

下架必须在一个数据库事务中完成：

1. 条件更新 `user_chart`：仅当状态仍为 `published` 时改为 `unpublished`。
2. 保存 `reviewNote`、`reviewedAt` 和 `reviewerUserId`。
3. 按 `cid` 删除公共 `chart` 记录。

事务成功后清理：

- 所有 `chart-list:*` Redis 缓存。
- 当前 `chart-detail:<cid>` Redis 缓存。

事务任一步失败都不允许出现“投稿已下架但公共图表仍存在”或相反的部分状态。

## 用户工作台

- 状态文案增加“已下架”。
- 已下架图表展示下架原因。
- 用户可以编辑、删除或重新提交已下架图表。
- 重新提交时清空旧下架原因和审核信息，状态进入 `pending`。

## 管理端交互

- 标签页显示当前列表数量。
- 待审核详情区显示“通过并发布”和“拒绝并退回”。
- 已发布详情区显示“下架原因”和“确认下架”。
- 下架成功后，从当前已发布列表移除并选择下一项。
- 操作期间禁用按钮；接口失败保留列表和选择状态并原位展示错误。

## 错误处理

- 未登录：`401`。
- 非管理员：`403`。
- 参数或空下架原因：`400`。
- 图表不存在：`404`。
- 图表状态已变化：`409`。
- 事务失败：`500`，不保留部分更新。

## 验收标准

- 用户创建页能运行当前代码预览。
- 预览 iframe 带 sandbox，用户代码不在主页面执行。
- 移动端创建页预览不破坏表单布局。
- 管理员可以在“已发布”标签页看到用户投稿。
- 下架原因为空时无法提交。
- 下架后公共列表和详情立即不可访问。
- 用户工作台显示“已下架”和下架原因。
- 用户修改已下架投稿后可再次提交审核。
- 普通用户无法调用下架 API。
- 前后端测试、构建和真实浏览器链路通过。
